# ตัวบันทึกภาพกล้อง

เว็บแสดงว่ากล้องเห็นอะไร**ตอนนี้** ตัวนี้เก็บว่ากล้องเคยเห็นอะไร — อัดวิดีโอจากทุกกล้อง
ต่อเนื่องเป็นคลิปละ 10 นาที ลง `D:/CCTV` จบคลิปหนึ่งก็เริ่มคลิปถัดไปทันที
เมื่อไดรฟ์ใกล้เต็มจึงค่อยทิ้งคลิปเก่าสุดของแต่ละกล้อง

```sh
npm run record          # อัดไปเรื่อย ๆ
npm run record:once     # อัดคลิปเดียวแล้วจบ (ใช้เวลา 10 นาที)
```

| ตัวเลือก | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `--out` | `D:/CCTV` (หรือ `CCTV_DIR`) | ที่เก็บ |
| `--minutes` | `10` | ความยาวคลิป — คลิปถัดไปเริ่มทันทีที่อันนี้จบ |
| `--free-gb` | `20` | กันที่ว่างไว้เท่านี้ ถ้าต่ำกว่าจะทิ้งคลิปเก่าสุด |
| `--samples` | `24` | จำนวนเฟรมต่อคลิปที่เอาไปนับรถ |
| `--workers` | `8` | นับพร้อมกันกี่คลิป |

## โครงสร้างที่ได้

```
D:/CCTV/
  ITICM_BMAMI0074/
    2026-09-10/
      13-29-16.mp4      วิดีโอ 10 นาที ตรงจากกล้อง ไม่มีกรอบทับ
      13-39-20.mp4
    2026-09-10.csv      หนึ่งบรรทัดต่อคลิป
```

หน้าเว็บเล่นคลิปไล่ตามเวลาที่อัด จบอันหนึ่งก็ต่ออันถัดไป — และเพราะคลิปถัดไปอัดเสร็จ
ไปแล้วตั้งแต่ก่อนอันปัจจุบันจะเล่นจบ การ์ดจึงไม่มีจังหวะต้องรอ

ไฟล์ถูกเขียนในชื่อ `<เวลา>.writing.mp4` ก่อน แล้วค่อยเปลี่ยนชื่อเมื่อ ffmpeg เขียนเสร็จ
(`server.js` ข้ามไฟล์ `.writing.` ตอนไล่รายการ) การ์ดจึงไม่มีทางหยิบไฟล์ที่ยังเขียนไม่จบ

## ทำไมใช้ ffmpeg ไม่ใช้ OpenCV

**ไม่ต้อง decode เลย** ตรวจด้วย ffprobe แล้วพบว่า 29 จาก 30 กล้องที่ Longdo ให้มา
เป็น **H.264 ที่ 25fps อยู่แล้ว** ซึ่งเป็นสิ่งที่เบราว์เซอร์เล่นได้พอดี ไม่มีอะไรต้องแปลง
`-c:v copy` จึงคัดลอกสตรีมลงไฟล์ตรง ๆ กิน CPU แทบไม่มี และได้คุณภาพเดิมของกล้อง

มีตัวเดียวคือ **`ITICM_BMAMI0188` ที่ส่งมาเป็น HEVC** ซึ่งเบราว์เซอร์ส่วนใหญ่เล่นไม่ได้
เฉพาะตัวนั้นจึงเข้ารหัสใหม่เป็น H.264 (`libx264 -preset veryfast -crf 23`) — วัดผลจริง
ได้ไฟล์ที่ ffprobe อ่านกลับมาเป็น `h264` ยาว 60.000 วินาทีเป๊ะ

โค้ดจำ codec ของแต่ละกล้องไว้ตั้งแต่รอบแรก การ probe เป็นการเปิด HLS ใหม่หนึ่งครั้ง
และคำตอบไม่เปลี่ยนระหว่างรอบ จึงจ่ายแค่ครั้งเดียวต่อการรันหนึ่งครั้ง

ใส่ `-movflags +faststart` ด้วย ไม่งั้น index จะไปอยู่ท้ายไฟล์ และเบราว์เซอร์ต้องโหลด
ครบทั้ง ~90 MB ก่อนจะขึ้นเฟรมแรกได้

## ทำไมไม่มีกรอบตรวจจับในคลิปแล้ว

ของเดิมอ่านคลิปกลับมาวาดกรอบทุกเฟรม ที่ 70ms ต่อเฟรม ตอนคลิปยาว 4 วินาทีก็พอไหว
แต่ **10 นาทีที่ 25fps คือ 15,000 เฟรม = GPU 17 นาที ต่อกล้องต่อคลิป** — ทำไม่ได้เลย
เมื่อมี 29 กล้องและมีเวลาแค่ 10 นาที

แทนที่ด้วยการ**สุ่มวัด**: คลิปที่อัดเสร็จแล้วถูกสุ่มอ่าน 24 เฟรมกระจายทั่วคลิป นับรถทีละเฟรม
แล้วเก็บค่าเฉลี่ยลง CSV คอลัมน์เดิม (`at,total,car,motorcycle,bus,truck`)

ไม่ได้ใช้ tracker เพราะสองเฟรมที่สุ่มมาห่างกันครึ่งนาที ไม่มีรถคันไหนอยู่ในทั้งสองเฟรม
จึงไม่มีอะไรให้ตามต่อ — ค่าเฉลี่ยของแต่ละเฟรมคือคำตอบของคำถามที่ถามจริง ๆ ว่า
"สิบนาทีนี้แยกนี้แน่นแค่ไหน"

ถ้าต้องการนับรถแบบตามทีละคัน ใช้ `detector/` ซึ่งทำงานที่ 7-8 fps บนกล้องที่มีคนเปิดดูอยู่

การนับรอบก่อนหน้าเกิด**ระหว่างที่รอบใหม่กำลังอัดอยู่** ไม่ใช่คั่นระหว่างรอบ เพราะโมเดล
เป็นส่วนเดียวที่ยังช้า และช่องว่างตรงนั้นคือภาพที่ไม่มีใครเก็บ

## พื้นที่

วัดจริงหนึ่งรอบ: **28 กล้อง คลิปละ 1 นาที รวม 249 MB** (เฉลี่ย 8.9 MB ต่อกล้องต่อนาที)

| | ขนาด |
|---|---|
| ต่อกล้อง ต่อคลิป 10 นาที | ~89 MB |
| ทั้ง 28 กล้อง ต่อรอบ 10 นาที | **~2.5 GB** |
| ต่อชั่วโมง | ~15 GB |

D: ว่าง 219 GB กันไว้ 20 GB จึงเก็บย้อนหลังได้ **ราว 13 ชั่วโมง** ก่อนจะเริ่มทิ้งของเก่า

`free_space()` ทิ้ง**ทีละรอบทั่วทุกกล้อง** ไม่ใช่ไล่ทิ้งกล้องต่อกล้อง ประวัติของทุกกล้อง
จึงยาวเท่า ๆ กัน ไม่ใช่กล้องหนึ่งหายทั้งวันขณะที่อีกกล้องยังครบ หนึ่งรอบที่ทิ้งได้พื้นที่
เท่ากับหนึ่งรอบที่อัด ไดรฟ์จึงกลับมาเหนือเส้นภายในหนึ่งถึงสองรอบ

## เรื่องกล้องที่ค้าง

รอบแรกที่วัดใช้เวลา 194 วินาทีสำหรับคลิป 60 วินาที เพราะกล้องตัวเดียวที่ไม่ยอมจบ
ค้างทั้งรอบไว้ — และรอบที่ตามมาคือภาพจาก**ทุกกล้อง**ที่ไม่มีใครได้อัด

ระยะผ่อนผันจึงเหลือ 30 วินาที พอสำหรับ faststart เขียน index ใหม่ท้ายคลิป ไม่พอสำหรับ
กล้องที่ค้าง และมี `-rw_timeout 20000000` (20 วินาที) ให้ ffmpeg เลิกเองเมื่อสตรีมเงียบ

`communicate()` ไม่ใช่ `wait()` เพราะ stderr ของ ffmpeg เป็น pipe — สตรีมที่พ่น error
จนเต็ม buffer จะทำให้ ffmpeg ค้างรอคนอ่าน และไม่มีใครอ่านจนกว่ามันจะจบ
