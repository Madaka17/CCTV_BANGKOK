# ตัวบันทึกภาพกล้อง

เว็บแสดงว่ากล้องเห็นอะไร**ตอนนี้** ตัวนี้เก็บว่ากล้องเคยเห็นอะไร — เก็บภาพจากทุกกล้อง
เป็นระยะ พอหมดวันก็ต่อเป็นวิดีโอหนึ่งไฟล์ แล้วลบทิ้งเมื่อเกินกรอบที่ตั้งไว้

```sh
npm run record          # เก็บไปเรื่อย ๆ
npm run record:once     # เก็บรอบเดียวแล้วจบ (ไว้ทดสอบ)
```

| ตัวเลือก | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `--out` | `D:/CCTV` (หรือ `CCTV_DIR`) | ที่เก็บ |
| `--interval` | `300` | วินาทีระหว่างรอบ (5 นาที) |
| `--keep-days` | `5` | เก็บกี่วัน |
| `--workers` | `8` | ดึงพร้อมกันกี่กล้อง |
| `--video-fps` | `10` | อัตราเล่นของวิดีโอที่ต่อแล้ว |

## โครงสร้างที่ได้

```

      04-57-52.mp4

```

แต่ละรอบอัดวิดีโอจริง 6 วินาทีจากทุกกล้อง ไม่ใช่ภาพนิ่ง เพราะภาพห่างกัน 10 นาที
อ่านเป็นการจราจรไม่ได้เลย — ถนนแค่ดูต่างกันไปเรื่อย ๆ ส่วนวิดีโอไม่กี่วินาทีบอกได้ทันที
ว่าแยกนั้นรถติดหรือไม่ หน้าเว็บเล่นคลิปไล่ตามเวลา จบอันหนึ่งก็ต่ออันถัดไป

## กรอบตรวจจับในคลิป

อัดเสร็จแล้วอ่านกลับมาใส่กรอบอีกรอบ ไม่ได้ใส่ตอนกำลังอัด เพราะ `FlowTracker`
ใช้ 70ms ต่อเฟรม คลิป 6 วินาทีที่ 15 fps จึงใช้ 5.3 วินาที ถ้าทำระหว่างอ่านสตรีม
จะตามไม่ทันและคลิปจะขาด แต่พอแยกออกมาก็ไม่ติดนาฬิกาของสตรีมอีก

ตัว tracker รันโมเดลทุกเฟรมที่ 3 แล้วไล่กรอบระหว่างนั้นด้วย optical flow เฟรม 90 เฟรม
จึงใช้โมเดลแค่ 25 ครั้ง ไม่ใช่ 90 ครั้ง — และแต่ละคันได้สีประจำตัว ตามไปได้ว่าคันไหนคือคันไหน

วัดจริงทั้งรอบ: 24/28 กล้อง 729 คัน **290 วินาที** จากงบรอบละ 600 วินาที
## เรื่องระยะห่างระหว่างรอบ

รอบหนึ่งวัดได้ **290–342 วินาที** แยกเป็นการเปิดสตรีมกับอัดคลิป และการใส่กรอบ
ซึ่งกิน 70ms ต่อเฟรม (คลิป 6 วินาทีที่ 15 fps = 5.3 วินาทีต่อกล้อง)

ตั้งไว้ที่ 5 นาที (300 วินาที) ซึ่งรอบมักเกินเล็กน้อย พอเกิน loop จะเริ่มรอบใหม่ทันที
**จังหวะจริงจึงอยู่ราว 5–5.7 นาที ไม่ใช่ 5 เป๊ะ** ไม่ใช่ความผิดพลาด แต่ควรรู้ไว้

ผลข้างเคียงที่ต้องยอมรับ: **GPU แทบไม่ว่างเลย** ซึ่งไปแย่งกับการตรวจจับสดตอนมีคนเปิดดู
กล้องเดี่ยว ถ้าอยากได้ 5 นาทีเป๊ะและ GPU ว่างบ้าง ให้ลด `CLIP_SECONDS` จาก 6 เหลือ 4
(เฟรมที่ต้องใส่กรอบลดจาก 90 เหลือ 60)

**เก็บทุก 10 วินาทีทำไม่ได้** ต้องเปิดสตรีมค้าง 29 เส้นพร้อมกัน ซึ่งชนกับแบนด์วิดท์ที่วัดไว้
ใน `public/js/app.js` — แต่ละสตรีมกิน 0.3–6.8 Mbps และแปดเส้นขนานกันแชร์ได้แค่ 2.5 Mbps

## ต้องลง OpenH264 ก่อน

วิดีโอเข้ารหัสเป็น **H.264** เพราะเบราว์เซอร์เล่นได้แค่นั้น ไม่ใช่เพราะเรื่องขนาดไฟล์

ตอนแรกโค้ดใช้ mp4v ซึ่ง**ผิด** — OpenCV อ่านกลับได้สบาย จึงผ่านการทดสอบมาได้ แต่
MPEG-4 Part 2 ไม่ใช่ codec ที่เบราว์เซอร์เล่นใน `<video>` การ์ดบนเว็บเลยได้ไฟล์ที่
แสดงได้แค่จอดำ

OpenCV ต้องการ `openh264-2.5.0-win64.dll` วางไว้ข้าง cv2:

```sh
curl -Lo oh.bz2 https://ciscobinary.openh264.org/openh264-2.5.0-win64.dll.bz2
bunzip2 oh.bz2
mv oh detector/.venv/Lib/site-packages/cv2/openh264-2.5.0-win64.dll
```

GitHub release ของ Cisco ไม่มีไฟล์แนบแล้ว ต้องโหลดจาก CDN ของเขา ซึ่งเป็นที่เดียวกับ
ที่ Firefox ใช้ และ `.venv/` อยู่ใน `.gitignore` ไฟล์นี้จึงไม่ถูก commit ต้องลงเองเมื่อย้ายเครื่อง

**ตรวจว่าได้ H.264 จริงด้วยการอ่าน fourcc กลับมา ไม่ใช่ดูแค่ว่าเปิดไฟล์ได้** — ต้องได้
`'h264'` ถ้าได้ `'FMP4'` แปลว่ายังเป็น mp4v อยู่

เทียบขนาดจริง 20 เฟรม 704×576: **H.264 1.08 MB / mp4v 3.54 MB**
