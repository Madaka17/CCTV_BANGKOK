# ตัวตรวจจับรถ

นับรถในภาพจากกล้อง ด้วย YOLO แล้วส่งผลให้หน้าเว็บ **ไม่เขียนอะไรลงดิสก์** — ผลอยู่ใน
หน่วยความจำ ค่าใหม่ทับค่าเก่า ปิดโปรแกรมแล้วหายหมด

## ติดตั้งครั้งเดียว

```sh
python3.11 -m venv detector/.venv
detector/.venv/bin/pip install ultralytics
```

โมเดลอยู่ใน `detector/weights/` (ดาวน์โหลดอัตโนมัติครั้งแรก) ทั้งสองโฟลเดอร์อยู่ใน `.gitignore`

## ใช้งาน

เปิดเว็บเซิร์ฟเวอร์ก่อน แล้วค่อยเปิดตัวนี้:

```sh
npm start &
detector/.venv/bin/python detector/detect.py --weights detector/weights/yolov8s.pt
```

| ตัวเลือก | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `--interval` | `60` | วินาทีระหว่างการกวาดกล้องทั้งหมด |
| `--focus-fps` | `2.0` | เฟรมต่อวินาทีของกล้องที่กำลังถูกดู |
| `--conf` | `0.25` | ความเชื่อมั่นขั้นต่ำ |
| `--imgsz` | `1280` | ขนาดภาพตอนอนุมาน |
| `--weights` | `yolov8s.pt` | โมเดล |

## วิธีทำงาน: ตรวจ + ติดตามด้วย optical flow

ดัดแปลงจากสคริปต์ `Track+DIS` — แนวคิดเดียวกัน ใช้ `cv2.DISOpticalFlow` แบบ ULTRAFAST เหมือนกัน

ปัญหาคือการตรวจจับช้ากว่าสตรีมมาก ถ้าวาดกรอบจากผลตรวจล่าสุดอย่างเดียว กรอบจะค้างอยู่ที่
ตำแหน่งเก่าแล้วกระโดดเป็นช่วงๆ วิธีแก้คือ:

- **ทุกเฟรม** — คำนวณ optical flow เทียบกับเฟรมก่อนหน้า แล้วเลื่อนกรอบทุกอันตามการเคลื่อนไหวจริง
- **ทุก 3 เฟรม** — รัน YOLO ใหม่ แล้วจับคู่กลับเข้ากับ track เดิมด้วย IoU
- **track id** ติดตัวรถไปเรื่อยๆ จนกว่าจะจับคู่ไม่ได้ติดต่อกัน 4 เฟรม

flow คำนวณที่ครึ่งความละเอียดเพราะเป็นส่วนที่แพงที่สุด

### ค่าที่ต้องปรับจากสคริปต์ต้นฉบับ

ต้นฉบับตั้งไว้สำหรับไฟล์วิดีโอ 25 fps ซึ่ง 5 เฟรม = 0.2 วินาที กรอบแทบไม่ขยับ
แต่สตรีมจริงได้ราว 7 fps ค่าเดิมทำให้ track ที่จับคู่ไม่ติดลอยอยู่ได้ถึง 6 วินาที
**นับได้ 110 คันทั้งที่ YOLO เห็น 50** เพราะกรอบผีทับกัน

| ค่า | ต้นฉบับ | ที่ใช้ | เหตุผล |
|---|---|---|---|
| `redetect_every` | 5 | **3** | ตรวจถี่ขึ้นเพราะเฟรมห่างกว่า |
| `max_age` | 30 | **4** | ลืมเร็วขึ้น ไม่ให้กรอบผีสะสม |
| `iou_threshold` | 0.3 | **0.2** | จับคู่หลวมขึ้น รถขยับเยอะกว่าระหว่างการตรวจ |

## สองโหมด

**กวาดทั้งหมด (ปิดไว้เป็นค่าเริ่มต้น)** — ไล่ทีละกล้อง กล้องละ 1 เฟรม เปิดด้วย `--interval 120`
แต่มันแย่งแบนด์วิดท์กับกล้องที่กำลังดูจนสตรีมตาย จึงปิดไว้

**เกาะติดกล้องที่ดูอยู่** — หน้าเว็บบอกว่ากำลังดูกล้องไหนผ่าน `/api/detect-focus?id=`
ตัวตรวจจับจะเปิด ffmpeg ค้างไว้กับกล้องนั้น แล้วตรวจ+ติดตามต่อเนื่องราว **7 fps**
ข้อมูลเก่าไม่เกิน 0.1-0.4 วินาที

focus จะถูกปล่อยเองถ้าหน้าเว็บเงียบไป 20 วินาที (ปิดแท็บ เลื่อนผ่าน ฯลฯ)

เหตุผลที่ต้องเปิด ffmpeg ค้าง: เปิดใหม่ทุกเฟรมใช้เวลาราว 5 วินาที เกือบทั้งหมดหมดไปกับ
การเชื่อมต่อ HLS ใหม่

## API

| เส้นทาง | คืนอะไร |
|---|---|
| `GET /detections` | ผลของทุกกล้อง เรียงตามจำนวนรถ |
| `GET /detections?id=X` | เฉพาะกล้องเดียว (ใช้ตอน poll ทุกวินาที ~3KB) |
| `GET /frame/<id>.jpg` | ภาพล่าสุดที่วาดกรอบแล้ว |
| `GET /focus?id=X` | บอกว่ากำลังดูกล้องไหน ต้องเรียกซ้ำทุก <20 วินาที |
| `GET /health` | สถานะโมเดล จำนวนรอบ และ fps ของ focus |

เว็บเซิร์ฟเวอร์ต่อให้ที่ `/api/detections`, `/api/detect-frame/<id>`, `/api/detect-focus`
**ถ้าตัวตรวจจับไม่ได้เปิด เว็บจะทำงานปกติแค่ไม่มีตัวเลขรถ**

## ข้อจำกัดที่ต้องรู้

ความแม่นยำขึ้นกับมุมกล้องมาก วัดจริงจากทั้ง 19 กล้อง:

| มุมกล้อง | ผล |
|---|---|
| มุมต่ำ มองตามถนน (พระราม 4, บางนา-ตราด) | 20-60 คัน แม่นดี |
| มุมสูงมากจากตึก (สาทร) | 1-2 คัน ทั้งที่มีเป็นร้อย |
| สตรีมความละเอียดต่ำ (204×328) | 0 คัน |

รถในภาพมุมสูงกว้างราว 10 พิกเซล ซึ่งเล็กเกินกว่าที่โมเดลที่เทรนกับ COCO จะจับได้
ถ้าต้องการกล้องมุมสูงต้องใช้โมเดลที่เทรนกับภาพมุมสูงโดยเฉพาะ เช่น VisDrone

`yolov8n` ที่ 640px (ค่าเริ่มต้นของ ultralytics) ตรวจได้ **0 คัน** บนถนนที่มีรถเป็นร้อย
`yolov8s` ที่ 1280px คือขั้นต่ำที่ใช้งานได้จริง

**ตัวเลขคือจำนวนรถในเฟรมนั้น ไม่ใช่จำนวนรถที่ผ่านไป** — ใช้บอกความหนาแน่นได้ ใช้นับปริมาณจราจรไม่ได้
